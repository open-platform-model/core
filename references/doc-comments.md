# Doc comments

Covers the three-tier comment rule for CUE definitions: the 6-line doc comment, the `// WHY` block,
SPEC.md Rationale, and how to cite an enhancement in a comment.

Every `//` block that ends on the line directly above a field or definition is that declaration's doc comment, and `cue lsp` hover, `Value.Doc()`, `cue def` and `task generate:index` replay it verbatim. One blank line ends the block; a comment separated from the field by a blank line is not hover text, and `cue fmt` preserves that blank line. Comments therefore go in three tiers:

1. **Doc comment, at most 6 lines.** The contract: what the field is and what a consumer must satisfy, optionally ending with `See SPEC.md § N.M`.
2. **`// WHY ...` block above the doc comment, separated from it by one blank line.** State a rationale once: a paragraph that restates a SPEC.md Rationale bullet collapses to that bullet's title in the closing pointer, and when several definitions share one rule, one carries the WHY block and the others a two-line pointer to it. Rationale that must stay next to the code: measured evaluator behavior, refuted spellings, `Was:` history. Reads in natural order (why, then what, then the field); the blank line is load-bearing, and closing it merges the two into one over-limit doc comment that `task docs:check` reports.
3. **`SPEC.md` Rationale.** The full argument, which `core-schema-edit` already requires.

**Enhancement references never go in a doc comment.** In all text (proposal, design, specs, docs and comments), cite an enhancement only as its id beside a reason in words: write the reason, then `(enhancement 0011)`, or `(enhancements 0010 and 0011)` for two. Never write an id alone, and never a decision number (`NNNN:Dn`, `NNNN Dn`, `NNNN:OQn`, a bare `D9`): the store has no decision numbers. A comment that holds only an id, such as `// WHY name: enhancement 0011`, is a lone id: write the reason. The reference belongs in the tier-2 `// WHY` block, separated from the doc comment by one blank line, because `cue lsp` hover, `Value.Doc()`, `cue def` and `task generate:index` replay a doc comment verbatim to someone who cannot open the enhancements store. Never cite a section, slice, phase or task number (`§8.1`, `slice C2`, `task 4.2`); they are not stable identifiers. `Was:` rename history is tier-2 rationale and follows the same rule. `*_pins.cue` fixtures are exempt from the tier rule: package `pins` is imported by nothing and docs-kit skips `*_pins.cue`, so no consumer, hover or generated page replays them (most pin fields are also hidden; the publish-gate pins are not). The id-beside-a-reason rule still holds there.

`task docs:check` fails on every doc comment over 6 lines. The script `.tasks/doc-check.sh` is kept byte-identical with `catalog_opm`'s copy; `task docs:lint` at the workspace root checks it. `*_pins.cue` fixture files are exempt; hidden `_` fields in schema files are not. Details and a before/after example in `.claude/skills/core-schema-edit/SKILL.md` § Writing comments.

The docs extractor (docs-kit contract C17) drops `// WHY` blocks and strips canonical enhancement citations from doc comments. A doc comment that reads badly once they are gone, or that cites an enhancement in prose, needs rewording at the source. `task docs:check` fails on every doc comment over 6 lines; `.tasks/doc-check.sh` is kept byte-identical with `catalog_opm`'s copy, and `task docs:lint` at the workspace root checks it. Details and a before/after example are in `.claude/skills/core-schema-edit/SKILL.md`, section "Writing comments".
