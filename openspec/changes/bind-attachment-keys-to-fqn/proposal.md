## Why

Every attachment map in core is keyed by contract FQN by convention only. `#ResourceMap`, `#TraitMap` and `#BlueprintMap` (the types of `#Component.#resources`, `#traits` and `#blueprints`) accept any string key, and the three `#Catalog` contract maps check only the key's form (`#ContractFQNType`). Nothing ties a key to the member's `metadata.fqn`. Yet every consumer reads the key as the member's identity: the library's render build (`library/opm/internal/renderstage/render.cue.tmpl`) indexes `#resources` and `#traits` by key to match demands, and `#Platform.#contracts` keys `defined` by the catalog map key. A component that attaches `container: res.#Container` validates in core and then demands a contract called `container` that no transformer supplies. A catalog listing a trait under another trait's key validates in core and publishes a contract under a name that is not the member's own.

The owner decided this in the beta.1 kernel plan walkthrough, task j3: "Bind attachment map keys to metadata.fqn on all five maps (component #resources/#traits/#blueprints and the catalog.cue member maps), as a hard vet error. Breaking core beta tightening: rewrite core's short-key pins and re-vet catalog_opm and the module fleet first (owner sign-off if a published catalog member is mis-keyed, 0021:D7 R5). appliesTo: keep, documented as unchecked; investigation filed as core#99." The supervisor's decision SD13 reads "all five maps" as the six attachment maps the sentence lists (three on `#Component`, three on `#Catalog`), and leaves `#Catalog.#transformers` unbound. SD14 folds two wave-1 follow-ups into this change, because they touch the same pin files: make the publish-gate pins in `src/pins/` non-hidden, and correct the text that says plain `cue vet` misses rule 1 of `#TraitOptionalGate`.

It implements no enhancement decision, so it carries no `enhancement.yaml`. 0021:D7:R5 is the sign-off rule this change stops on if it fires. It does not implement R5.

## What Changes

- **BREAKING: the component attachment maps bind key to fqn.** `#ResourceMap`, `#TraitMap` and `#BlueprintMap` become `[FQN=string]: #X & {metadata: fqn: FQN}`. A component entry whose key differs from its member's `metadata.fqn` fails `cue vet` with `conflicting values "<key>" and "<fqn>"` at `#resources.<key>.metadata.fqn` (or the `#traits` / `#blueprints` path). A short key such as `container:` is refused.
- **BREAKING: the catalog contract maps bind key to fqn.** `#Catalog.#resources`, `#traits` and `#blueprints` bind each member's `metadata.fqn` to its key, next to the existing `modulePath` and `catalogVersion` stamps. A member listed under another contract's key fails with the same conflicting-values error. The key stays typed `#ContractFQNType`. `#transformers` is not bound (SD13).
- **Pins.** Core's own short keys are rewritten to `(X.metadata.fqn): X` in `src/pins/component_names_pins.cue` and `src/pins/platform_and_match_pins.cue`, including the commented must-fail twins and the read-backs that index by the short key. `_pinContractKeyNotCompared` in `src/pins/catalog_pins.cue` asserts that core does not compare key and fqn. It becomes a commented must-fail case with the recorded error. New must-fail cases cover a mis-keyed component resource, trait and blueprint. New positive pins show that a correctly keyed entry validates in each of the six maps.
- **Publish-gate pins become non-hidden.** The seven pins that apply a publish gate (`_pinGateTraitPostureRequired` and `_pinGateTraitPostureAdvisory` over `#TraitOptionalGate`, plus the five `#CatalogMemberFQNGate` applications in `src/pins/identity_package_pins.cue`) lose their `_` prefix. `cue vet` checks a non-hidden field for completeness, so plain `task vet` now fails on an unstated `optional` posture. Measured during planning: all seven vet clean as non-hidden fields under plain `cue vet ./...` and `cue vet -c ./...`, and the rule-1 case then fails plain vet. The pin file headers and the `schema-pins` capability describe the exception.
- **Rule-1 text corrected.** `src/trait.cue` (the `_stated` comment), `SPEC.md` §5.1 (Shape comment, Constraints, Rationale) and the pin comments say that plain `cue vet` exits 1 on an unstated posture with the generic "some instances are incomplete" message and names no field, and that `cue vet -c` names the field. They no longer say that plain vet misses rule 1.
- **SPEC.md.** §3.1 `#Component` and §3.6 `#Catalog` state the binding rule (Constraints and Rationale). §3.6 drops "the contract maps do NOT stamp or bind `metadata.fqn`". §2.2, §3.1 and §3.3 keep `appliesTo` documented as unchecked and point at core#99. `src/INDEX.md` is regenerated, because the three map definitions gain doc comments.
- **Re-vet before merge.** The re-vet runs against this branch's core build, in scratch copies only: catalog_opm (`src/`), the modules fleet, opm-modules (read only), the CUE fixtures of the library, cli and opm-operator, and opm-operator `modules/opm_operator`. The results are written into `design.md`.

Not in this change: binding `#Catalog.#transformers` (SD13); binding `#ComponentTransformer`'s demand maps (`requiredResources` and the others, which SPEC §4.1 already states MUST equal the value's fqn); checking `appliesTo` (core#99); consumer pin bumps (each consumer bumps through its deps cascade after the core release).

## Release class

**MAJOR-class tightening per Principle I, shipped as `feat!` under the `@v2` beta break licence (Principle IV).** It advances `-beta.N` and does not move the module path. The PR title is `feat!: bind attachment map keys to the member's fqn`, and the squash body carries the migration note below as its `BREAKING CHANGE:` footer.

It does **not** force a `catalogs/opm` major, unless the re-vet finds a published member that is mis-keyed. The planning audit found none. It evaluated every published `opmodel.dev/catalogs/opm@v4` release from 4.1.0 to 4.6.0, the catalog_opm tags, catalog_opm main, the modules fleet (172 attachments) and opm-modules (114 attachments), and found 0 mismatches. If the re-vet finds a published mis-keyed member, the change still lands complete on the branch, the finding goes first in the report with exact paths, and the merge waits for the owner's sign-off (0021:D7:R5).

## Downstream consumers

- **catalog_opm**: every member is listed as `(X.metadata.fqn): X`, so nothing changes. It picks the change up through its core deps-cascade bump. The re-vet confirms this.
- **modules fleet and opm-modules**: components embed catalog wrappers (`bp.#StatelessWorkload`, `res.#Volumes`, `tr.#Expose`) that key by fqn. Nothing changes, and the change arrives with the core pin bump.
- **library**: the render template already indexes by fqn keys. Test-data catalogs and fixtures key by `(X.metadata.fqn)`. A library core pin bump (`lib-h2`, or the cascade) brings the change into its tests, and the re-vet covers the fixtures beforehand. A short key that a library user wrote by hand would now fail in the kernel's CUE build, which is the purpose of this change.
- **cli, opm-operator**: the same applies to their CUE test fixtures and to opm-operator's `modules/opm_operator`. The re-vet covers both. Neither needs a code change.
- **Third-party catalogs and modules**: cannot be audited. A hand-written short key fails `cue vet` after the core bump, with an error that names both strings.

## Migration note

BREAKING CHANGE: an attachment map key must equal the attached member's `metadata.fqn`. This covers `#Component.#resources`, `#traits` and `#blueprints` (`#ResourceMap`, `#TraitMap`, `#BlueprintMap`) and `#Catalog.#resources`, `#traits` and `#blueprints`. A key that differs fails `cue vet` with `conflicting values "<key>" and "<fqn>"` at `<map>.<key>.metadata.fqn`. Write each entry as `(X.metadata.fqn): X`, or embed the catalog's wrapper (`res.#Container`, `tr.#Expose`, `bp.#StatelessWorkload`), which already does. Replace short keys such as `container:` or `volumes:`. `#Catalog.#transformers` is unchanged. No published catalog member and no first-party module was found mis-keyed.
